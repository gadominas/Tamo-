## Recipes

Coding rules every app follows (https://github.com/gadominas/app-blueprints/tree/main/recipes). They describe how the code is written, not a feature, so they aren't listed in the script's `BLUEPRINTS` block or in Built with.

| Recipe | Version | Since app version | Deviations |
| --- | --- | --- | --- |
| [safe-startup](https://github.com/gadominas/app-blueprints/blob/safe-startup-v1.1.0/recipes/safe-startup.md) | 1.1.0 | 1.9.0 | Data files read in `loadData()`: the saved diary (`dienynas-plus-cache.json`, `diaryCache`) and AI token usage (`dienynas-plus-usage.json`), both on the phone (`FileManager.local`), not iCloud; chats and "what's new" files are read per child after the window is up; AI settings (`dienynas-plus-ai-settings.json`, local) are still read with the settings, because they are choices (the provider in use) and the key migration needs them. `write()` writes only `settings.json`; the usage guard lives in `aiWrite()`; the diary cache needs no guard, because it is only written with TAMO's fresh answer. The usage file is read in `loadData()` with the app's local file manager rather than `load()`, with the same split (not read → `loadIssues`; not valid JSON → `keepBroken()`, next to it as `dienynas-plus-usage.broken-<time>.json`); after the copy the fresh usage is saved at once, because usage is otherwise saved only after an AI call and the damaged file and its toast would stay until then. A damaged `settings.json` is saved over in the same run by the first-run branch of `loadSettings()`. The diary cache and AI settings (`dienynas-plus-ai-settings.json`) are not guarded, as before: a damaged cache reads as "nothing saved" and TAMO's next answer replaces it; damaged AI settings fall back to the defaults. The list handed over in pieces is the Ask chat (`chat`, slices of 20); `__boot` sets `window.DATA`, the name the page's `pageMain` reads, instead of `__INIT`. The app builds a new page when fresh data arrives and when the language or a grade scale changes: every page load goes through `App.show()` (shell, then `handOver()`), so no page has the diary inlined. With no diary saved yet, `__boot(null)` marks the page as started and keeps "Loading your diary…" until TAMO answers, because the first sign-in and the child picker can take longer than the 25 s stall note. The sign-in prompt (a native Alert) still comes before the window when no sign-in details are saved. The app's own refresh is the TAMO reload, 0.7 s after boot (not when a Shortcuts check just loaded the data); it runs even when a file wasn't read, since it writes only the diary cache and the widget snapshot. Nothing is saved on close: settings and AI files are saved at every change, the diary and the widget snapshot after every TAMO answer. `app` and `wv` are module variables set in `main()`, because the `App` class owns the window. The start-up log also notes how long TAMO took to answer (never error text, names or sign-in details); the placeholder, the stall and failure notes, the "couldn't read" toast (which also covers settings that weren't read), the "kept a copy and started it fresh" toast and the Start-up log row follow the app language. The Shortcuts check reads no data files itself; its **Open** goes through `main()` |
